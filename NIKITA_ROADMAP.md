# Roadmap Никиты: Product Application

**Роль:** разработка пользовательского продукта вокруг независимого Analysis Core  
**Зона:** backend, frontend, UI, хранение, задания, интеграция с CLI, сборка и демонстрация  
**Не входит:** таксономия, промпты, выбор дефектов, обработка содержимого документа, golden set и качество модели

Связанный документ: [INTEGRATION_CONTRACT.md](./INTEGRATION_CONTRACT.md).

## 1. Целевой результат

Пользователь загружает готовый документ, выбирает профиль проверки, запускает анализ и получает до 20 замечаний, привязанных к местам документа.

```text
Пользователь
    ↓
Web UI
    ↓
Backend API
    ↓
Job Runner
    ↓
CLI Михаила: файл + Review Pack + Model Config
    ↓
ReviewResult JSON
    ↓
Хранение → API → UI → Feedback
```

Приложение не анализирует содержание документа и не содержит промптов. Оно управляет жизненным циклом проверки и отображает результат Analysis Core.

- проверка и сохранение JSON;
- API статуса и результатов;
- UI загрузки, прогресса и замечаний;
- обработка ошибок;
- Docker Compose;
- стабильный демонстрационный сценарий.

### P1 — желательно для сильной демонстрации

- просмотр документа рядом с замечаниями;
- переход к странице и фрагменту;
- feedback по замечаниям;
- история запусков;
- выбор версии Review Pack;
- техническая диагностика запуска;
- резервный режим с сохранённым результатом.

### P2 — развитие после основного сценария

- авторизация и роли;
- multi-company изоляция;
- Review Pack Registry;
- MinIO/S3;

- корпоративный поиск;
- on-premise LLM;
- Confluence и другие коннекторы;
- Kubernetes/OpenShift;
- мониторинг и аудит production-уровня.

## 8. Этап 5. Реализовать Review Job

### Жизненный цикл

```text
queued
  → running
  → completed
  → failed
  → timed_out
  → cancelled
```

### Первый вариант

Для раннего MVP достаточно отдельного worker-процесса, который получает задания из PostgreSQL. После стабилизации интерфейса можно перейти на Celery + Redis.

### Задачи

- создавать `run_id`;
- создавать рабочую директорию запуска;
- копировать или предоставлять input-файл;
- выбирать Review Pack;
- собирать аргументы CLI без shell-конкатенации;
- запускать CLI отдельным процессом;
- читать `stdout` и `stderr` раздельно;
- ограничивать runtime;
- корректно завершать зависший процесс;
- сохранять exit code;
- проверять наличие `result.json`;
- валидировать результат по JSON Schema;
- атомарно обновлять статус задания;
- предотвращать двойной запуск одного job.

### Безопасный запуск

Аргументы передаются массивом, а не собранной shell-строкой:

```python
command = [
    "docreview",
    "analyze",
    "--file", str(input_path),
    "--pack", str(pack_path),
    "--run-id", str(job.id),
    "--output", str(result_path),
]
```

### Критерий готовности

Backend корректно обрабатывает каждый mock-сценарий и не зависит от текста логов CLI.

## 11. Этап 8. Экран результата

```text
┌────────────────────────────────┬──────────────────────────────┐
│ Документ                       │ Замечания                    │
│                                │                              │
│ Страница и подсветка фрагмента │ Severity                     │
```

### Задачи

- не предоставлять автоматическое переписывание документа;
- показывать имя и версию Review Pack;
- показывать понятную ошибку при частично недоступном документе.

## 15. Этап 12. Стабилизация демонстрации

### Обязательные сценарии

1. Успешный анализ документа.
2. Документ без замечаний.
3. Ошибка модели.
4. Ошибка парсинга.
5. Повторный запуск.
6. Feedback по замечанию.

### Резервный режим

Подготовить:

- заранее проверенный демонстрационный файл;
- сохранённый валидный `ReviewResult`;
- возможность включить mock endpoint конфигурацией;
- запись полного демонстрационного сценария;
- понятную инструкцию запуска.

### Нефункциональные проверки

- отсутствие зависаний UI;
- восстановление страницы по `review_id`;
- отсутствие потери результата после перезапуска;
- корректный timeout;
- защита от двойного запуска;
- читаемые ошибки;
- отсутствие секретов в логах;
- стабильная работа с кириллицей.

### Критерий готовности

Полный сценарий воспроизводится три раза подряд без ручного вмешательства в систему.

## 16. Этап 13. Представление платформенности

Для демонстрации универсальности не нужно реализовывать полноценный multi-tenant. Достаточно показать архитектурное переключение Review Pack.

### Минимальная демонстрация

```text
Документ NET
  + mts-data-mart Review Pack
  → замечания NET

Другой технический документ
  + generic-technical-spec Review Pack
  → замечания другого профиля
```

### Задачи Никиты

- вывести выбор Review Pack в UI;
- показать имя компании, тип и версию пакета;
- не зашивать NET-терминологию в интерфейс;
- использовать нейтральные сущности `document`, `review`, `finding`;
- предусмотреть `company_id` в моделях, даже если в MVP одна компания;
- не связывать UI с конкретными `defect_id`.

### Критерий готовности

Приложение демонстрирует, что новая компания подключается через другой Review Pack, а не через изменение кода.

## 20. Definition of Done Никиты

Технический контур Никиты завершён, если:

1. Пользователь может загрузить PDF или DOCX.
2. Приложение создаёт отдельное задание и не блокирует HTTP-запрос.
3. Worker безопасно запускает Analysis Core по согласованному CLI-контракту.
4. Приложение различает успешное выполнение, timeout и все основные ошибки.
5. Результат валидируется по версии JSON Schema.
6. Результат сохраняется и доступен после перезапуска.
7. UI отображает статус выполнения.
8. UI показывает до 20 замечаний с местом, цитатой и уточнением.
9. Пользователь может оставить feedback.
10. В UI нет логики конкретных дефектов NET.
11. Review Pack выбирается конфигурацией.
12. Mock и настоящий Analysis Core взаимозаменяемы.
13. Секреты и внутренние пути не возвращаются клиенту.
14. Проект запускается через Docker Compose.
15. Полный демонстрационный сценарий выполняется три раза подряд.

## 21. Первый практический инкремент

Первая версия должна пройти самый короткий вертикальный сценарий:

```text
Загрузить PDF
    ↓
Создать Review Job
    ↓
Вызвать mock CLI
    ↓
Прочитать ReviewResult JSON
    ↓
Показать список замечаний в браузере
```

Пока этот сценарий не работает целиком, не следует углубляться в визуальный polish, Celery, расширенную историю или production-инфраструктуру.
