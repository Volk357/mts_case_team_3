Техническая спецификация сервиса уведомлений

Назначение сервиса
Сервис принимает события от внутренних систем и доставляет уведомления
пользователям по выбранным каналам. Заменяет рассылку из монолита.

Границы решения
Сервис не хранит адресную книгу и не занимается сегментацией аудитории.
Шаблоны сообщений редактируются в отдельной системе.

Пользователи и роли
Оператор — просматривает журнал доставки. Администратор — управляет каналами.
Права выдаются по заявке.

Функциональные требования
Приём события по HTTP, постановка в очередь, доставка по каналу, повтор при сбое.
Количество повторов настраивается. Валидация входящего события выполняется
по возможности.

Внешние интерфейсы
POST /notifications — принять событие.
GET /notifications/{id} — состояние доставки.
Базовый адрес сервиса уточняется на этапе развёртывания.

| Поле        | Тип       | Описание                      |
| event_id    | string    | Идентификатор события         |
| channel     | string    | Канал доставки                |
| payload     | object    | Содержимое уведомления        |
| created_at  | timestamp | Момент создания события       |

NotificationRequest содержит поля выше. NotificationResponse описан в приложении.

Модель данных
Событие хранится до подтверждения доставки. Срок хранения TBD.

Обработка ошибок
При недоступности канала выполняется повтор. Поведение при исчерпании
повторов не описано.

Требования к безопасности
Доступ к API по токену. Адрес получателя и текст уведомления передаются
в открытом виде внутри контура.

Нефункциональные требования
Нагрузка до 500 RPS. Время ответа p95 не более 200 мс.

Критерии приёмки
Сервис принимает событие и доставляет его. Проверка выполняется на staging
и т.д.
