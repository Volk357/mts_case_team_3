# Совместная отладка Product Application и Analysis Core

## Граница ответственности

Product Application отвечает за загрузку файла, очередь, запуск отдельного процесса,
лимиты, проверку контракта, сохранение и показ результата. Analysis Core отвечает за
разбор документа, смысл замечаний и формирование ReviewResult.

Если результат ядра некорректен по смыслу или формату, исправление делается в ядре.
Backend не переименовывает defect ID, не дописывает обязательные поля, не исправляет
summary, не обрезает лишние findings и не вводит исключения для отдельных дефектов.

## Диагностический artifact

После завершения процесса worker сохраняет приватный файл:

```text
data/runs/<run_id>/artifacts/integration-diagnostic.json
```

Он содержит:

- фактический argv запуска без shell-интерполяции;
- exit code;
- ограниченный stderr и признак его обрезки;
- точные ошибки приёмки результата приложением.

Artifact не выдаётся через публичный API и не добавляется в Git. Он может содержать
локальные пути и диагностический текст ядра, поэтому перед передачей его нужно
просмотреть. Содержимое документа и полный ReviewResult в экспорт не включаются.

## Экспорт по идентификатору проверки

Из корня репозитория:

```powershell
apps/api/.venv/Scripts/python.exe apps/api/scripts/export_review_diagnostic.py `
  <review_id> --output diagnostics/<review_id>.json
```

`review_id` берётся из адреса страницы `/reviews/<review_id>`. Команда объединяет
статус из БД с process artifact. Существующий файл не перезаписывается без `--force`.

## Порядок передачи дефекта

1. Воспроизвести проблему на минимальном документе без чувствительных данных.
2. Приложить экспортированный diagnostic JSON и, если допустимо, этот документ.
3. Указать ожидаемое и фактическое поведение, версию core, Review Pack и schema.
4. Владелец ядра воспроизводит точную команду из поля `execution.command`.
5. Исправление смысла или ReviewResult вносится в Analysis Core.
6. Добавляется regression fixture, затем выполняется общая команда `npm run check`.

Для недоступной модели и timeout допустим пользовательский retry. Ошибки схемы,
идентичности запуска и инвариантов результата не повторяются автоматически: сначала
исправляется поставка ядра или согласованный контракт.

## Изменение контракта

Контракт нельзя менять только в одном компоненте. Один change set включает:

1. новую версию `contracts/review-result.schema.json` и запись в CHANGELOG;
2. валидные и невалидные fixtures;
3. обновление Analysis Core и его версии;
4. регенерацию TypeScript-типов;
5. обновление таблицы совместимости;
6. контрактные, worker и E2E-тесты.

Major-версия меняется при несовместимом изменении. Поддерживаемое расширение схемы
может получить новую minor-версию. До прохождения всех проверок Product Application
продолжает отклонять неизвестную major-версию целиком.
