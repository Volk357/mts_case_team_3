# Политика хранения и удаления

**Версия:** 1.0  
**Статус:** политика MVP зафиксирована; автоматическое удаление отключено

## Сроки хранения

| Данные | Срок | Точка отсчёта | Поведение в MVP |
|---|---:|---|---|
| Исходный файл документа | 90 дней | Последняя активность: максимум из даты загрузки и времени завершения всех связанных jobs | После срока только помечается как доступный для предлагаемой явной очистки |
| Рабочая директория запуска (`input`, `output`, `artifacts`) | 14 дней | Terminal timestamp (`completed_at`, `failed_at`, `timed_out_at` или `cancelled_at`) | После срока целиком только помечается как доступная для предлагаемой явной очистки |
| `ReviewJob.raw_result`, findings и feedback | Бессрочно в MVP | — | Хранятся для аудита и измерения качества до санкционированного tenant purge |

Job в `queued` или `running` не имеет terminal timestamp, поэтому его артефакты
не могут считаться доступными для очистки. Повторная проверка сдвигает срок хранения
оригинала: отсчёт ведётся от последнего завершившегося job этого документа.

Срок означает только дату eligibility и не является командой удаления. Исполняемая
политика представлена `RetentionPolicy`; она вычисляет даты, не обращается к БД или
файловой системе. Настройка `DOCREVIEW_AUTOMATIC_RETENTION_ENABLED` в MVP принимает
только `false`, поэтому случайно включить фоновую очистку конфигурацией невозможно.

## Явная очистка в MVP

В MVP нет scheduler, фонового retention worker или удаления при чтении, запуске и
завершении проверки. Файл, артефакт или запись удаляются только отдельной будущей
операцией, явно подтверждённой оператором компании. Истечение срока само по себе
ничего не меняет.

Рабочая директория создаётся атомарно в `runs/{run_id}` и удаляется только целиком:
частичная очистка `input`, `output` или `artifacts` запрещена, чтобы сохранённый job
не ссылался на неполный запуск. Каталоги `.preparing-*`, оставшиеся после аварийного
завершения подготовки, считаются orphaned только после отдельного grace period и
могут удаляться исключительно явной служебной процедурой. `queued` и `running`
workspace, а также директории без подтверждённого terminal job очистке не подлежат.

До появления такой операции администратор может получить только dry-run список:
tenant, тип ресурса, resource ID, storage key, точка отсчёта и дата eligibility.
Отсутствие ресурса при повторном планировании не должно считаться ошибкой.

## Контракт будущего tenant-scoped purge

`TenantPurgePlan` фиксирует безопасную границу будущей реализации, но намеренно не
содержит метода исполнения. План обязан:

- иметь один `company_id`; каждый target повторно подтверждает принадлежность ему;
- содержать автора, причину и timezone-aware UTC timestamp для аудита;
- использовать UUID сущностей и только относительные POSIX storage keys без `..`;
- отклонять смешивание tenants до любого обращения к storage;
- исполняться идемпотентно и отдельно для каждого target;
- сначала зафиксировать санкционированную DB-транзакцию, затем удалять физические
  объекты; частичный сбой должен допускать безопасный повтор;
- удалять связанные записи в порядке feedback → findings → job → document и не
  затрагивать общие Review Packs или данные другой компании.

Перед реализацией purge нужно отдельно добавить авторизацию, legal hold, audit log,
dry-run/confirmation API и правила резервных копий. Эти механизмы не входят в MVP.

## Настройки

| Переменная | Значение по умолчанию | Ограничение |
|---|---:|---|
| `DOCREVIEW_DOCUMENT_RETENTION_DAYS` | `90` | 1–3650 дней |
| `DOCREVIEW_ARTIFACT_RETENTION_DAYS` | `14` | 1–365 дней |
| `DOCREVIEW_AUTOMATIC_RETENTION_ENABLED` | `false` | В MVP только `false` |
