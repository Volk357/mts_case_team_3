# 03. Модель данных приложения

## Цель

Надёжно хранить документы, задания, исходные результаты Analysis Core, замечания и пользовательскую обратную связь.

## Зависимости

- JSON Schema результата;
- выбранная СУБД;
- согласованная политика хранения файлов.

## Последовательность работ

### NIK-03-01. Спроектировать сущности

- `Document`;
- `ReviewJob`;
- `Finding`;
- `FindingFeedback`;
- `ReviewPackReference`;
- предусмотреть `Company` и `User`, не реализуя полную авторизацию;
- определить связи и правила удаления.

### NIK-03-02. Статусы Review Job

- определить state machine;
- разрешить только валидные переходы;
- сохранить timestamps каждого этапа;
- отделить `error_code` от пользовательского сообщения;
- предусмотреть повторный запуск как новый job.

### NIK-03-03. Хранение результата

- сохранять исходный `ReviewResult` целиком;
- нормализовать findings для UI и фильтрации;
- не изменять смысл данных ядра;
- сохранять версии schema/core/pack/model/prompts;
- хранить SHA-256 документа.

### NIK-03-04. Реализация БД

- создать SQLAlchemy-модели;
- создать Alembic migrations;
- создать repositories;
- добавить транзакции для завершения job;
- добавить индексы по status, document_id и created_at.

### NIK-03-05. Политики хранения

- определить срок хранения исходного файла;
- определить срок хранения диагностических артефактов;
- не удалять данные неявно в MVP;
- предусмотреть последующее tenant-scoped удаление.

## Артефакты

- ER-диаграмма;
- модели и migrations;
- repositories;
- описание state machine;
- seed/test fixtures.

## Проверки

- миграции применяются к пустой БД;
- миграции откатываются на один шаг;
- невалидный переход статуса отклоняется;
- результат переживает перезапуск backend;
- feedback не изменяет исходный Finding;
- повторная обработка результата не создаёт дубли.

## Критерий завершения

Документ, job, результат и feedback создаются и читаются через repository layer, а завершение job выполняется атомарно.
