# 09. Feedback

## Цель

Собрать проверяемую оценку полезности замечаний и передать её Михаилу без автоматического изменения Analysis Core.

## Зависимости

- сохранённые Finding;
- feedback API;
- согласованный словарь решений.

## Последовательность работ

### NIK-09-01. Модель решения

- `accepted`;
- `false_positive`;
- `allowed_exception`;
- `already_described`;
- `not_relevant`;
- необязательный комментарий;
- timestamp и пользователь/сессия.

### NIK-09-02. UI

- компактные кнопки на Finding Card;
- объяснить различия решений;
- показывать сохранённое состояние;
- позволить изменить решение;
- комментарий открывать по необходимости;
- не мешать основному чтению замечаний.

### NIK-09-03. Backend

- upsert feedback;
- валидация принадлежности finding review;
- защита от случайных дублей;
- сохранение истории изменений при необходимости;
- отделение feedback от raw ReviewResult.

### NIK-09-04. Выгрузка

- JSONL или CSV для Михаила;
- включить run, finding, pack/model/prompt versions и decision;
- не включать секреты и лишние персональные данные;
- фильтровать по периоду и Review Pack.

### NIK-09-05. Продуктовые метрики

- доля принятых findings;
- false positive rate по defect ID;
- доля неоценённых findings;
- среднее время до решения при наличии данных;
- не подменять этим Recall@20 Михаила.

## Артефакты

- FeedbackControls;
- feedback endpoint;
- таблица `finding_feedback`;
- export-команда/endpoint;
- базовая агрегированная статистика.

## Проверки

- повторный клик не создаёт дубли;
- изменение решения сохраняется;
- feedback не меняет исходный result;
- export связан с точными версиями запуска;
- UI восстанавливает решение после reload.

## Критерий завершения

По каждому замечанию можно сохранить решение, а Михаил получает машиночитаемую выгрузку для анализа качества.
