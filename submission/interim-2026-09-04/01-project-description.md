# DocReview Platform — описание проекта, промежуточная версия

**Дата состояния:** 3 сентября 2026 года.  
**Стадия:** работающий технологический каркас, контур качества и отдельные части
пользовательского сценария; интеграция реального Analysis Core с UI продолжается.

## Краткая аннотация

DocReview Platform — платформа предварительного ревью больших корпоративных
документов. Аналитик загружает готовый PDF или DOCX, выбирает набор правил своей
компании и получает ограниченный список конкретных мест, которые могут быть
непонятны разработчикам или требуют уточнения. Решение не переписывает документ и
не заменяет эксперта: окончательное решение по каждому замечанию принимает человек.

Первый прикладной профиль создаётся для технических заданий продукта NET на новые
потоки и витрины данных. Общая механика не зависит от NET: знания о структуре,
типичных дефектах, исключениях и промптах вынесены в сменный Review Pack.

## Проблематика

Техническое задание может содержать таблицы примерно на 300 полей. Перед началом
разработки его последовательно читают аналитики, разработчики и тестировщики, но из-за
объёма внимание замыливается. На ручной анализ уходит порядка 2–3 часов. Часть
неоднозначностей обнаруживается только во время разработки или тестирования, что
возвращает документ аналитику и создаёт повторные согласования, доработку реализации
и дополнительное тестирование.

Имеющееся решение публикует автоматические отчёты в комментарии Confluence, однако
его замечания оцениваются пользователями как недостаточно полезные. При этом
предоставленные примеры уже прошли ревью тремя командами: естественных ошибок в них
мало, поэтому для измерения полноты нужен управляемый synthetic golden set.

## Актуальная постановка задачи

Создать дополнительный контроль качества финального документа перед передачей в
разработку. Система должна:

- находить максимум существенных дефектов; пропуск ошибки считается хуже лишнего
  вопроса к аналитику;
- возвращать ориентировочно 10–15 наиболее полезных замечаний и никогда больше 20;
- для каждого замечания указывать место, цитату, возможную проблему и то, что стоит
  уточнить, не редактируя исходный текст;
- учитывать шаблон, таксономию и сознательные исключения компании;
- работать в закрытом контуре с внутренней OpenAI-совместимой LLM;
- подключать новую команду или компанию заменой Review Pack, а не форком приложения.

## Выбранное техническое решение

Решение разделено стабильным CLI/JSON-контрактом на два независимых контура.

1. **Analysis Core** получает файл, Review Pack и конфигурацию модели; выполняет
   детерминированные и LLM-проверки; проверяет привязку цитат; ранжирует кандидатов и
   возвращает `ReviewResult` JSON.
2. **Product Application** принимает и безопасно хранит документ, создаёт задание,
   запускает CLI отдельным процессом, контролирует timeout, валидирует результат,
   хранит историю и отдаёт состояния и findings в UI через HTTP API.
3. **Review Pack** хранит YAML-конфигурацию структуры документа, таксономии,
   исключений и промптов. Благодаря этому продуктовый движок остаётся универсальным.

Модель разработки доступна по внутреннему OpenAI-совместимому endpoint через
WireGuard; используется Qwen3 30B на RTX 4090. Внешние модельные API в целевой
production-архитектуре не требуются.

## Уже реализованные компоненты

### Analysis Core и качество

- рабочий LLM-review pipeline и детерминированный слой;
- YAML-таксономия и шаблон;
- генератор эталонных синтетических документов;
- 5 документов, 65 заранее внесённых дефектов 25 типов;
- scoring по месту и по сочетанию места с типом дефекта;
- негативные контроли и автоматические тесты;
- доступная локальная Qwen3-модель.

### Product Application

- Python/FastAPI backend, React/TypeScript frontend и единые команды разработки;
- JSON Schema результата, exit codes и сгенерированные TypeScript-типы;
- CLI-совместимый mock Analysis Core с успешными и ошибочными сценариями;
- модель данных, миграции, state machine review и tenant isolation;
- безопасная загрузка PDF/DOCX, проверка формата и атомарное хранение;
- durable DB queue, worker, отдельный process runner, timeout, отмена и retry;
- приём и schema-validation результата, проекция findings;
- Documents API и асинхронный Reviews API с idempotency и polling;
- UI загрузки документа.

## Предварительные результаты

- Контур качества фиксирует промежуточную точность 83% на слепой внутренней
  разметке и 58% на внешней разметке кейсодателя. Эти цифры требуют закрепления
  единой методикой и не считаются финальной оценкой продукта.
- Synthetic golden set воспроизводимо содержит 65 дефектов: 40 присутствующих в
  тексте, 21 дефект отсутствия содержания и 4 удалённых раздела.
- Product Application: 213 backend-тестов пройдено, 1 платформенно-зависимый тест
  пропущен; покрытие 91,97%. Mock Core: 45 тестов, покрытие 95,82%. Frontend:
  14 тестов, production-сборка проходит.
- Загрузка документа, постановка review в очередь, безопасный polling и выдача
  findings уже представлены отдельными контрактами. Полный пользовательский E2E с
  реальным ядром ещё не заявляется как завершённый.

## Ограничения и открытые вопросы

- Требуется упаковать зависимости Analysis Core и привести его запуск к общему CLI.
- Нужны повторные замеры Recall@20, Precision@20 и Citation Accuracy по согласованной
  процедуре, включая чистые документы.
- Внешняя выборка мала; synthetic corpus не заменяет оценку кейсодателем.
- Ещё не завершены каталог Review Packs, экран результата, feedback и Docker Compose.
- Нужно подтвердить второй, не связанный с NET профиль, чтобы доказать платформенность.
- Извлечение части структуры и гиперссылок DOCX пока ограничивает некоторые проверки.

## План до финальной версии

1. Зафиксировать исполняемый CLI Analysis Core и интегрировать его с готовым worker.
2. Провести полный E2E: upload → review → локальная LLM → findings → UI.
3. Реализовать каталог и выбор Review Pack без передачи произвольного пути.
4. Завершить progress/result UI, навигацию к месту и пользовательский feedback.
5. Прогнать golden set, чистые контроли и документы кейсодателя; оформить отчёт.
6. Добавить generic Review Pack и второй демонстрационный документ.
7. Собрать Docker Compose, обработать демонстрационные ошибки и подготовить backup demo.
