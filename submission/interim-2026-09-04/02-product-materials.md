# Продуктовый brief

## Пользователь и его задача

Первичный пользователь — аналитик, который готовит техническое задание перед
передачей разработчикам. Его задача — обнаружить потенциально неоднозначные,
неполные или противоречивые места до начала разработки, не перечитывая вручную
сотни полей несколько раз.

Вторичные участники — разработчики и тестировщики: они получают более ясные
требования и реже возвращают документ на уточнение. Покупателем или владельцем
решения может быть руководитель продуктовой, аналитической или quality-функции.

## Продуктовая гипотеза

Если дать аналитику перед передачей документа в разработку 10–15 конкретных,
локализованных замечаний, сформированных с учётом правил его компании, то доля
существенных неоднозначностей, обнаруженных до разработки, вырастет, а время команд
на повторное чтение и согласование снизится.

## Ценностное предложение

**Для аналитика:** дополнительная пара глаз на большом документе, которая показывает
куда смотреть и что уточнить, но не присваивает себе экспертное решение.

**Для команды:** меньше поздних возвратов требований и связанных переделок.

**Для компании:** единый on-premise механизм контроля документов, который адаптируется
через версионируемый пакет корпоративных знаний.

## Почему это платформа

Общими остаются загрузка, очередь, модель жизненного цикла, вызов LLM, формат
замечаний, UI и feedback. Для новой компании меняется Review Pack:

- ожидаемая структура документа;
- таксономия дефектов;
- разрешённые исключения;
- prompts/few-shot примеры;
- правила severity, ранжирования и лимита результата.

Таким образом, кейс NET — первый профиль универсального document review engine.

## Вклад AI Product и связь с реализацией

| Продуктовое решение | Основание | Техническая реализация |
|---|---|---|
| Оптимизировать полноту с бюджетом | Кейсодатель считает пропуск хуже лишнего вопроса, но назвал 10–15 замечаний идеалом и 20 потолком | Candidate generation, verification/ranking, `maxItems: 20`, Recall@20 |
| Не переписывать текст | Пользователю нужен контроль, а не соавтор | В finding только location, quote, problem и clarification |
| Проверять финальный документ | Основная боль возникает перед передачей в разработку | Асинхронный upload/review flow вместо realtime-редактора и MCP |
| Учитывать намеренные исключения | Не вся формальная неполнота является ошибкой | Исключения и enabled checks в Review Pack |
| Работать внутри контура | Внешние API запрещены в production | OpenAI-compatible model gateway и конфигурация локальной Qwen3 |
| Масштабироваться на компании | Задача хакатона шире одного кейса | Нейтральное приложение и YAML Review Packs без hardcoded defect IDs |
| Учиться на решениях эксперта | Истинная полезность определяется аналитиком | Отдельная FindingFeedback-модель; API/UI и выгрузка входят в ближайший план |

## Альтернативы и позиционирование

- В отличие от общего spell/grammar checker продукт ищет смысловые и структурные
  дефекты конкретного типа документа.
- В отличие от чат-интерфейса результат воспроизводим, привязан к месту и ограничен
  контрактом.
- В отличие от жёстко прошитого корпоративного решения правила версионируются вне
  кода приложения.
- В отличие от внешнего SaaS целевой контур допускает локальные модели и не требует
  передачи документов наружу.

# Границы MVP и пользовательский сценарий

## Основной сценарий

1. Аналитик открывает приложение и загружает финальный PDF или DOCX.
2. Приложение проверяет размер, расширение, сигнатуру файла и безопасно сохраняет его.
3. Аналитик выбирает опубликованный Review Pack для своего типа документа.
4. Backend создаёт idempotent review job и сразу возвращает идентификатор.
5. UI показывает состояние; worker запускает Analysis Core отдельно от HTTP-запроса.
6. Core читает документ и Review Pack, выполняет формальные и LLM-проверки через
   внутренний model gateway, проверяет цитаты и оставляет не более 20 findings.
7. Backend валидирует JSON, сохраняет исходный результат и публичные проекции.
8. Аналитик видит 10–15 приоритетных карточек: место, цитату, возможную проблему и
   предлагаемое уточнение.
9. Аналитик принимает или отклоняет каждое замечание и при необходимости исправляет
   исходный документ самостоятельно.

## В MVP входит

- PDF и DOCX;
- один документ на один review;
- выбор только из разрешённых Review Packs;
- локальная OpenAI-совместимая LLM;
- формальные и LLM-проверки;
- асинхронное выполнение, polling, timeout и понятные ошибки;
- максимум 20 локализованных findings;
- решение аналитика по finding;
- история как минимум в пределах demo-контура;
- два профиля на демонстрации: NET и generic technical specification.

## В MVP не входит

- автоматическое переписывание документа;
- замена обязательного человеческого ревью;
- realtime-подсказки во время набора текста;
- интеграция с Confluence/MCP;
- обучение модели после каждого клика;
- произвольная загрузка пользователем исполняемых rules/prompts;
- OCR сканов низкого качества и все офисные форматы;
- полноценная enterprise-аутентификация и горизонтальное масштабирование.

## Состояния сценария

| Состояние | Что видит пользователь | Текущее состояние реализации |
|---|---|---|
| Upload | Зона загрузки, проверки формата и размера | Реализовано |
| Pack selection | Разрешённые пакеты с названием и версией | Следующий этап |
| Waiting/analysis | Безопасная стадия и polling | Backend реализован, UI предстоит |
| Result ready | Список findings и навигация | API реализован, UI предстоит |
| Failed/timed out | Понятная ошибка и возможность нового запуска | Backend реализован, UI предстоит |
| Feedback | Решение и комментарий аналитика | Модель данных реализована, API/UI предстоят |

## Демонстрационная граница

Минимально убедительная финальная демонстрация: два разных документа проверяются тем
же приложением и ядром, но разными Review Packs. Переключение профиля не требует
изменения или новой сборки кода приложения.

# Критерии успеха и план проверки гипотезы

## Иерархия метрик

### 1. Качество обнаружения — главный уровень

| Метрика | Предварительный целевой порог | Статус |
|---|---:|---|
| Recall@20 по существенным дефектам | ≥ 80% | Требует итогового прогона |
| Citation/Location Accuracy | ≥ 95% | Требует итогового прогона |
| Precision@20 на оценке эксперта | ≥ 60% | Есть промежуточные оценки, методику нужно унифицировать |
| Число findings | обычно 10–15, всегда ≤ 20 | Ограничение зафиксировано контрактом |
| Ложные срабатывания на чистом контроле | не более 3 на документ | Требует итогового прогона |

Recall выбран главным критерием по прямой обратной связи кейсодателя: пропущенная
ошибка хуже дополнительного вопроса. Precision остаётся ограничителем доверия и
когнитивной нагрузки.

### 2. Пользовательская полезность

| Метрика | Рабочая гипотеза |
|---|---:|
| Доля findings, признанных полезными (`accepted`) | ≥ 60% |
| Доля документов, где найдено хотя бы одно принятое замечание | ≥ 70% документов с известными дефектами |
| Снижение времени первого ревью | ≥ 30% относительно ручных 2–3 часов |
| Понятность замечания | ≥ 4 из 5 по оценке аналитика |

Эти пороги пока не достигнуты и не должны подаваться как результат. Для их проверки
нужен наблюдаемый пользовательский прогон и сбор feedback.

### 3. Техническая готовность

- review создаётся без ожидания модели;
- повторная отправка не создаёт дубликат;
- каждый completed result проходит JSON Schema validation;
- внутренние пути, prompts, model config и диагностические сообщения не попадают в API;
- два Review Pack работают без изменения приложения;
- E2E demo проходит повторяемо, предусмотрен резервный сценарий.

## Что уже измерено

- Synthetic corpus: 5 документов, 65 дефектов, 25 типов; инварианты генерации
  выполнены.
- В материалах контура качества зафиксирована precision 83% на слепой внутренней разметке и
  58% на внешней разметке кейсодателя. Выборки и методика должны сопровождать
  следующие значения.
- Автоматические проверки Product Application: backend 213 passed / 1 skipped,
  coverage 91,97%; mock core 45 passed, coverage 95,82%; frontend 14 passed.

## План эксперимента до финала

1. Зафиксировать версии Core, модели, prompts, taxonomy и synthetic corpus.
2. Запустить одинаковый pipeline на пяти испорченных и пяти чистых документах.
3. Посчитать Recall@20 отдельно для `presence`, `absence`, `section_removed` и для
   LLM/deterministic слоёв.
4. Посчитать precision и ложные срабатывания слепой экспертной оценкой без показа truth.
5. Проверить дословность/локализуемость цитаты автоматикой и выборочной ручной проверкой.
6. Сравнить с существующим Confluence-решением на одном наборе, если baseline доступен.
7. Провести наблюдаемый сценарий с аналитиком: время, принятые findings, оценка ясности.
8. Разобрать промахи по типам, изменить только версионируемый Review Pack/Core и
   повторить замер без изменения тестового набора.

## Защита от самообмана

- synthetic truth создаётся одновременно с детерминированной мутацией, а не после
  просмотра ответа модели;
- чистые версии документов являются негативным контролем;
- результаты показываются по классам дефектов, а не только одной средней цифрой;
- внутренняя и внешняя разметка не смешиваются;
- целевые пороги, промежуточные измерения и фактически достигнутые значения маркируются
  отдельно.

# Допущения, риски и способы проверки

| Допущение или риск | Вероятность / влияние | Что делаем до финала | Сигнал решения |
|---|---|---|---|
| Synthetic defects не отражают реальные причины возврата ТЗ | Высокая / высокая | Внешняя слепая оценка на документах кейсодателя и разбор расхождений | Recall и precision не проседают критически относительно synthetic set |
| При приоритете recall пользователь утонет в придирках | Средняя / высокая | Жёсткий предел 20, целевой диапазон 10–15, ranking и feedback | Полезными признаются ≥60%, время просмотра приемлемо |
| Намеренные пропуски вызовут false positive | Высокая / средняя | Явные exclusions и `not applicable` в Review Pack, чистые контроли | Не более 3 FP на чистом документе |
| LLM выдаст неверную цитату или JSON | Средняя / высокая | Проверка цитаты, schema validation, детерминированный fallback и безопасная ошибка | 100% принятых результатов валидны, location accuracy ≥95% |
| Контекст 4096 токенов недостаточен для больших таблиц | Высокая / высокая | Структурный parsing/chunking и выбор релевантного контекста | Длинный тестовый документ не теряет ключевые типы дефектов |
| Локальный model endpoint недоступен на защите | Средняя / высокая | Connectivity preflight, timeout, сохранённый безопасный demo-result | Основной и резервный demo проходят по чек-листу |
| Analysis Core не совпадёт с CLI/JSON-контрактом приложения | Средняя / высокая | Упаковка зависимостей, adapter и contract tests до UI-интеграции | Один CLI одинаково запускается evaluation runner и worker |
| «Платформа» останется декларацией одного кейса | Средняя / высокая | Второй generic pack и документ другой структуры | Оба профиля работают без изменения приложения |
| Документы или VPN-ключ попадут в публичный Git | Низкая / критическая | Ignore rules, synthetic data, проверка истории и логов | В репозитории нет реальных документов, ключей и цитат из них |
| Двух разработчиков не хватит на полную enterprise-версию | Высокая / средняя | Жёсткая граница MVP; auth/масштабирование оставить roadmap | Стабильный основной сценарий важнее числа функций |

## Ключевые открытые вопросы к кейсодателю

1. Какой минимальный Recall@20 будет считаться убедительным на финальной оценке?
2. Какие типы замечаний являются обязательными независимо от общего лимита?
3. Как формально учитывать дефект отсутствия, у которого нет дословной цитаты?
4. Какие исключения должны быть глобальными, а какие — частью конкретного шаблона?
5. Можно ли получить обезличенный baseline существующего Confluence-решения на том же
   тестовом наборе?
6. Какой feedback аналитика считать истинной меткой: первое решение или результат
   последующего согласования с разработчиком?
