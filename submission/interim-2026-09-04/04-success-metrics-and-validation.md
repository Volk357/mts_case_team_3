# Критерии успеха и план проверки гипотезы

## Иерархия метрик

### 1. Качество обнаружения — главный уровень

| Метрика | Предварительный целевой порог | Статус |
|---|---:|---|
| Recall@20 по существенным дефектам | ≥ 80% | Требует итогового прогона |
| Citation/Location Accuracy | ≥ 95% | Требует итогового прогона |
| Precision@20 на оценке эксперта | ≥ 60% | Есть промежуточные оценки, методику нужно унифицировать |
| Число findings | обычно 10–15, всегда ≤ 20 | Ограничение зафиксировано контрактом |
| Ложные срабатывания на чистом контроле | не более 3 на документ | Требует итогового прогона |

Recall выбран главным критерием по прямой обратной связи кейсодателя: пропущенная
ошибка хуже дополнительного вопроса. Precision остаётся ограничителем доверия и
когнитивной нагрузки.

### 2. Пользовательская полезность

| Метрика | Рабочая гипотеза |
|---|---:|
| Доля findings, признанных полезными (`accepted`) | ≥ 60% |
| Доля документов, где найдено хотя бы одно принятое замечание | ≥ 70% документов с известными дефектами |
| Снижение времени первого ревью | ≥ 30% относительно ручных 2–3 часов |
| Понятность замечания | ≥ 4 из 5 по оценке аналитика |

Эти пороги пока не достигнуты и не должны подаваться как результат. Для их проверки
нужен наблюдаемый пользовательский прогон и сбор feedback.

### 3. Техническая готовность

- review создаётся без ожидания модели;
- повторная отправка не создаёт дубликат;
- каждый completed result проходит JSON Schema validation;
- внутренние пути, prompts, model config и диагностические сообщения не попадают в API;
- два Review Pack работают без изменения приложения;
- E2E demo проходит повторяемо, предусмотрен резервный сценарий.

## Что уже измерено

- Synthetic corpus: 5 документов, 65 дефектов, 25 типов; инварианты генерации
  выполнены.
- В материалах контура качества зафиксирована precision 83% на слепой внутренней разметке и
  58% на внешней разметке кейсодателя. Выборки и методика должны сопровождать
  следующие значения.
- Автоматические проверки Product Application: backend 213 passed / 1 skipped,
  coverage 91,97%; mock core 45 passed, coverage 95,82%; frontend 14 passed.

## План эксперимента до финала

1. Зафиксировать версии Core, модели, prompts, taxonomy и synthetic corpus.
2. Запустить одинаковый pipeline на пяти испорченных и пяти чистых документах.
3. Посчитать Recall@20 отдельно для `presence`, `absence`, `section_removed` и для
   LLM/deterministic слоёв.
4. Посчитать precision и ложные срабатывания слепой экспертной оценкой без показа truth.
5. Проверить дословность/локализуемость цитаты автоматикой и выборочной ручной проверкой.
6. Сравнить с существующим Confluence-решением на одном наборе, если baseline доступен.
7. Провести наблюдаемый сценарий с аналитиком: время, принятые findings, оценка ясности.
8. Разобрать промахи по типам, изменить только версионируемый Review Pack/Core и
   повторить замер без изменения тестового набора.

## Защита от самообмана

- synthetic truth создаётся одновременно с детерминированной мутацией, а не после
  просмотра ответа модели;
- чистые версии документов являются негативным контролем;
- результаты показываются по классам дефектов, а не только одной средней цифрой;
- внутренняя и внешняя разметка не смешиваются;
- целевые пороги, промежуточные измерения и фактически достигнутые значения маркируются
  отдельно.
